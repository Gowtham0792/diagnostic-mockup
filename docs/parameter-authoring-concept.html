Concept note · Option D

Split the parameterization tool by audience

One web-based authoring tool holds all the dependency and consistency logic. The field ZF [pro] Diagnostics Suite only fetches a finished, validated parameter set by ID and writes it to the ECU. The two are linked through a shared back end.

1The problem today

All the intelligence — trailer-type rules, sensor/modulator compatibility, "not-permitted" combinations, plausibility checks — is hand-coded inside the diagnostic GUI that the installer uses. That GUI is expensive to specify, build and regression-test, and it still asks an installer with little system knowledge to make engineering decisions.

2The concept — two tools, one back end

Separate who defines the configuration from who applies it to a trailer. The hard engineering logic moves to a web authoring tool used by a small number of ZF / OEM engineers. The field tool becomes a thin client.

Web authoring tool no licence · linked

  • Browser-based, reached by a plain link — no dongle, no per-seat licence.
  • Used by ZF / OEM application engineers to build one validated parameter set per trailer variant.
  • Carries all the dependency & consistency logic (e.g. drawbar ⇒ 4S/3M only; front-axle sensor ⇒ 4-sensor layout).
  • On publish, the back end mints a short Configuration ID.
  • UI to be modelled separately.

ZF [pro] Diagnostics Suite (field)

  • Installer opens Parameterization, types (or scans) the Configuration ID.
  • Pulls the finished set from the back end — no rule engine on board.
  • Shows a plain-language summary + a short whitelist of site values (tyre size, service interval).
  • Writes to the ECU and reports completion back to the back end.
Link, not licence. The authoring tool is not sold or licence-gated. It is linked to the diagnostic suite only through the back end: the diagnostic suite trusts any valid Configuration ID the back end can resolve. Access control on authoring is a separate, lightweight login.

3End-to-end flow

From "engineer decides the braking configuration" to "trailer ECU is parameterized" — the Configuration ID is the hand-off.

5Why this is cheaper to build

Effort saved

  • Rules written & regression-tested once, not per field-tool screen.
  • Field tool requirements shrink to: ID entry, fetch, summary, whitelist edit, write, report.
  • New trailer variant = new authored template — no field-tool release.
  • Authoring tool has few users → lighter UX, faster iteration, no dongle logistics.

Open questions to resolve

  • Offline case — cache the last resolved set on the diagnostic PC for no-connectivity workshops?
  • ID format & anti-typo (checksum, QR, length).
  • Template versioning — can a published ID be superseded, and what does the field tool show?
  • Who may author, and how is that login managed?
  • Back-end ownership — existing ZF cloud service vs. new.
